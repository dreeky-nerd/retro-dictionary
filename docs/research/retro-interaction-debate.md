# XD-SW6400의 작은 키를 어떻게 누를 것인가 — 상호작용 대안 토론

작성일: 2026-10-01. 범위는 **iPhone 세로 화면의 입력 경험**이다. 앱 UI 구현이나 완성 시안이 아니라, 다음 동작 시제품에서 반증할 가설이다. 기준 기종의 키 위치·기능은 [CASIO XD-SW6400 설명서](https://www.casio.com/content/dam/casio/global/support/manuals/exword/pdf/003-ja/comb/XD-SW6400_JA.pdf)와 [기존 조사](casio-sw6400-analysis.md)를 따른다. 사용자가 거부한 전체 기기 축소와 큰 6버튼 대체안을 다시 추천하지 않는다.

## 판단의 출발점

사용자가 원하는 차별점은 **원래 QWERTY 10열 3행, 사전 단축키, 중앙의 작은 필기 패널, 방향·결정 키가 실제 검색을 움직이는 경험**이다. 이는 외형만 닮은 검색 앱으로는 충족되지 않는다. 동시에 빈번한 검색에서 오입력과 반복 피로가 크면 향수만으로 유지되지 않는다. 여러 방식을 보여주더라도 기본 입력 방식은 하나로 좁혀야 한다.

두 종류의 확대를 혼동하면 안 된다. 키캡 글자를 크게 보이게 하는 일은 **시각적 판독**을 돕는다. 손가락이 실제로 누를 수 있는 영역의 폭을 넓히는 일은 **운동 정확도**를 돕는다. 한 화면에 10열을 모두 보이는 한, 화면 폭을 예컨대 390pt로 잡으면 한 열의 이론상 최대 폭은 39pt다. 좌우 여백과 열 간격을 주면 더 작다. 이 수치는 기기별 측정값이 아니라 폭의 예시이며, 세로 확대는 이 가로 제약을 바꾸지 못한다. Apple의 일반 버튼 권장 터치 영역은 44×44pt이고 간격도 중요하다. 이는 모든 작은 키가 자동 실패한다는 판정선이 아니라, 기본 가정에 불리한 설계 신호다. 작은 목표에서 손가락 터치 정밀도 자체가 성능을 제한한다는 실험 연구도 있다. [Apple Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons), [Apple Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Bi 외, FFitts Law, CHI 2013](https://research.google/pubs/ffitts-law-modeling-finger-touch-with-fitts-law/).

## 대안 비교 — 일부러 약점을 먼저 본다

| --- | --- | --- | --- | --- |
| **A. 같은 기기의 ‘타이핑 작업면’으로 접근**. 펼친 기기를 잠깐 보여준 뒤 베젤·빈 하드웨어를 화면 밖으로 밀고, 원래 상대 위치의 키와 LCD를 키운다. | **배열 완전 고정**. 키의 순서·상대 위치·사전 키·방향 키 유지. 카메라/크롭만 이동. | 작은 전체 모형보다 읽기 쉽고, 한 물체를 가까이 보는 연출이라 정체성이 강하다. 새 자판 학습이 거의 없다. | 10열이 동시에 보이면 가로 키 폭은 거의 늘지 않는다. A+C/B 검증에 실패할 때만 논의. |

**더 단순한 선택:** A를 화면의 기본 장면으로 쓰되, 키를 잘못 누를 때만 B를 켜고 C를 적극적인 보조 입력으로 제공한다. 다만 이것을 기능 세 가지의 동시 출시 제안으로 읽어서는 안 된다. 첫 검증에서는 A 단독과 A+C를 비교하고, B는 정확도 문제가 남을 때만 작은 실험으로 붙이는 편이 판단이 빠르다. 시스템 키보드는 접근성·긴 단어 입력을 위한 선택적 우회로일 수 있으나 이 앱의 대표 조작으로 내세우면 핵심 정체성이 약해진다.

## 한글·일어 입력에서 생기는 숨은 비용

- **한글**: 물리 원형의 로마자 QWERTY에 한글 자모를 어떤 방식으로 대응할지 아직 정하지 않았다. 키캡에 자모를 겹쳐 쓰면 글자 가독성이 떨어지고, 영문 각인을 유지하며 두벌식처럼 조합하면 화면의 입력 상태와 키의 의미가 어긋날 수 있다. 영어 알파벳 검색의 성공을 한국어 입력 성공으로 간주할 수 없다.
- **일본어**: 로마자→가나 조합, 가나→한자 변환, 사전 표제어 자동완성은 서로 다른 단계다. `k`를 누를 때마다 표제어 후보가 즉시 바뀌는 방식은 미완성 음절과 충돌할 수 있다. 조합 중 글자, 변환 후보, 사전 검색 후보를 화면에서 분리하고, 결정 키가 어느 후보를 확정하는지 명시해야 한다. 원기기는 로마자/가나 입력과 필기 입력을 지원하지만, 여기서 제안한 후보 UI가 원기기와 같다는 뜻은 아니다. [XD-SW6400 설명서](https://www.casio.com/content/dam/casio/global/support/manuals/exword/pdf/003-ja/comb/XD-SW6400_JA.pdf).
- **예측 후보**는 자주 찾는 표제어까지의 누름 수를 줄일 가능성이 있지만, 첫 글자부터 그럴듯한 단어를 띄우는 일은 정확한 입력이 어려운 문제를 가릴 수도 있다. 희귀 단어·신조어·고유명사와 오타 수정은 별도로 평가해야 한다. 후보 선택을 위해 손이 LCD까지 왕복한다면 이득도 줄어든다.

## 추천과 폐기 기준

**추천할 경쟁 가설은 둘이다.** A는 원형 자판의 연속성을 살리고 **짧은 철자를 친 뒤 사전 후보를 방향·결정 키로 탐색하는 리듬**을 기본 상호작용으로 삼는다. 완전한 단어를 빠르게 타이핑하도록 강요하지 않는 것이 핵심이지만, 후보가 잘 맞지 않는 희귀어에는 약하다. C는 원래 작은 필기판을 크게 열어 실제 입력 면적을 확보한다. 한자처럼 자판으로 찾기 어려운 항목에서 더 독특한 해결책이며, 일반 단어의 반복 필기에는 약하다. 다음 시제품에서는 A와 A+C를 비교해 C가 실질적 이득을 주는지 판단한다. B는 A의 작은 키를 정밀하게 고르는 실험으로 가치가 있지만, 접촉→확대→놓기 동작을 매 글자의 기본 규칙으로 강제하지 않는다. 이것은 단순히 화면 두 개를 전환하면 문제가 해결된다는 주장이 아니다.

검증은 실기 iPhone 세로 화면에서 실시한다. 영어 짧은/긴 단어, 한글 조합어, 일어 로마자 입력·한자 변환, 읽기 모르는 한자를 과제로 두고, **첫 검색 성공률·수정 횟수·검색 완료 시간·하루 여러 차례 사용 후 주관적 피로**를 기록한다. 한 손/양손, 작은 화면, 큰 글자, VoiceOver를 분리해 본다. 다음 수치는 **제안하는 의사결정 기준이지 기존 연구 결과가 아니다**.

1. A 단독에서 문자 키 오입력 때문에 검색 과제의 20% 이상이 수정된다면 ‘10열 고정 자판만으로 충분하다’는 가설을 폐기한다. 크롭·애니메이션을 더해 해결된다고 주장하지 않는다.
2. A+C에서 긴 단어 입력 시간 또는 반복 피로가 시스템 키보드 대비 현저히 나쁘거나, 한글·일어의 인식/조합 후보 오선택이 잦으면 C를 **특수 문자/모르는 한자용**으로 축소한다. 영어·한글 일반 입력 해법이라고 홍보하지 않는다.
3. B가 오입력을 줄여도 검색 시간과 피로를 늘리거나 VoiceOver에서 동등한 선택 경로를 제공하지 못하면 기본 입력에서는 폐기한다.
4. 사용자가 첫 화면을 XD-SW6400의 자판·필기판·방향키로 알아보지 못하면 A의 크롭 범위와 전환 연출부터 다시 설계한다. 반대로 외형 인지도가 높아도 실제 검색 반복을 포기한다면 그 안은 제품 기본값으로 채택하지 않는다.

원기기의 키압·소리·필기 인식 성능, 실제 iPhone의 물리적 누름 면적과 오입력률은 이 문서로 검증하지 않았다. 특히 **원형 키 배열 고정**, **일부 구역 재배치 허용**, **원본 전체의 위치·비율까지 완전 고정**은 서로 다른 목표다. 마지막 목표는 모든 하드웨어를 한 화면에 담는 순간 작은 키 문제를 되돌리므로, 정적 감상 화면의 목표로만 남긴다.
